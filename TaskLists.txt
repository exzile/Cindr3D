# PHASE OCC-16: Fillet corner auto-reordering (Fusion-parity 1mm corners)
# ══════════════════════════════════════════════════════════════════════════════
#
# PROBLEM (verified 2026-05-29):
#   Filleting a line edge at 1mm fails when an adjacent circular-rim fillet
#   already exists. OCC Build() throws. The existing combined-on-base fallback
#   also fails (all edges combined on base = null at 1mm). But sequential
#   application in the RIGHT ORDER succeeds:
#     notch (r6.71 circle) → vertical line edge at 1mm = OK ✅
#     vertical line edge → notch at 1mm = notch fails ❌
#     all-at-once combined at 1mm = null ❌
#     all-at-once combined at 0.5mm = OK ✅
#   Fusion always solves this at 1mm because ASM's corner solver is more
#   robust. Our OCC can ALSO do it — but only in the right order.
#
# ROOT CAUSE (why order matters):
#   When the circular edge is filleted first, its torus blend reshapes the
#   adjacent faces so the subsequent line-edge fillet has enough topology to
#   close the corner blend. When the line edge goes first, it meets an un-blended
#   notch corner that OCC's single-pass vertex blender cannot solve.
#
# APPROACH: Topology-aware sequential fallback
#   After ALL existing fallbacks fail (combined, vertex-neighbor, arc-first,
#   combined-on-base, per-edge sequential), try one more: partition the edge set
#   by geometry type and vertex adjacency, then apply the groups in a topology-
#   aware order. Specifically: round edges (circles/arcs) before line edges that
#   share a vertex with them.
#
# ╔══════════════════════════════════════════════════════════════════════════════╗
# ║ CRITICAL CONSTRAINT: all fallbacks MUST honour the requested radius exactly. ║
# ║ No silent clamping. No radius reduction. A failure should produce a clean    ║
# ║ error + guidance — never a degenerate result. (Fusion's behaviour.)         ║
# ╚══════════════════════════════════════════════════════════════════════════════╝
#
# BRANCH: fix/fillet-corner-reorder (cut from master)

# ── Track B: Topology-aware sequential fallback ───────────────────────────────

[x] OCC-16.B1 — topologicalFilletOrder(partition): Array<number[]>
#   Pure function: given an EdgePartition (from A3), returns an ORDERED list of
#   edge-id groups to apply as sequential combined passes. Rules:
#     1. Round edges adjacent to linear edges go in group 1 (fillet the arc/
#        circle first so OCC has the blended topology to close the corner).
#     2. Linear edges adjacent to round edges go in group 2 (applied on the
#        intermediate body after group 1 is done).
#     3. Round edges NOT adjacent to linear, and linear edges NOT adjacent to
#        round, are each combined in their own pass (or folded into group 1/2
#        respectively if they don't conflict).
#   Example for the real failing case:
#     partition.round = [notchRimId]  (r6.71 circle, adjacent to vertId V)
#     partition.linear = [topEdgeId] (line, adjacent to same vertId V)
#     → returns [[notchRimId], [topEdgeId]]
#   Returns [] if input has no adjacency (caller skips this path).
#   Pure function, no OCC calls — unit-testable with mocked partitions.
#   File: src/engine/occ/ops/filletOrder.ts (new file)

[x] OCC-16.B2 — occFilletEdgeSetsTopologicalWithInstance(oc, body, edgeSets, opts)
#   New exported function in fillet.ts. Applies the topology-ordered sequential
#   strategy:
#     1. Call A3's partitionEdgesByTopology on the seed edges + the base body
#     2. Call B1's topologicalFilletOrder for the ordered plan
#     3. If plan.length <= 1 (no meaningful adjacency), return null early
#        (let caller fall through to existing fallbacks — not a regression)
#     4. For each group in the plan:
#        a. Build OccFilletEdgeSet[] for that group (same radius from matching
#           edgeSets input — each group inherits the radius of its source edges)
#        b. Call occFilletEdgeSetsWithInstance on the current running body
#        c. If result is null or invalid (isOccShapeValid check): dispose + return null
#        d. Dispose the previous running body; update running = result
#     5. After all groups: validate the final body with the result-correctness
#        guard (seed anchors consumed — same logic as edgeModApply's guard).
#        If any seed anchor survives → degenerate result → dispose + return null.
#     6. Return the final valid body, or null if any step failed.
#   Disposal discipline: every intermediate body that is replaced must be
#   disposed immediately (do NOT hold on to them — WASM heap pressure).
