# SYMPTOM: single fillets work; two fillets whose edges meet at a shared vertex
# fail — BRepFilletAPI_MakeFillet.Build() throws (seen in console: "combined
# fillet failed" → "arc-first sequential fallback" → result=null). User expects
# the corner where the two fillets meet to be rounded (Fusion does this).
#
# FUSION OPTION MODEL (verified from SDK headers 2026-05-28):
#   FilletFeatureInput: isG2(), isRollingBallCorner(), isTangentChain()
#   FilletEdgeSet:      continuity (Tangent=G1 / Curvature=G2), tangencyWeight (0.1-2.0)
#   - isRollingBallCorner = the CORNER SOLUTION at vertices where fillets meet:
#       true  → rolling-ball (spherical) corner blend
#       false → setback corner (fillets stop short; mitered patch fills the gap)
#     "For an asymmetric fillet only a setback solution is supported." (header)
#   - isG2 / continuity = the fillet SURFACE cross-section continuity (G1 vs G2).
#   ⇒ These are INDEPENDENT axes. Corner-solution ≠ surface-continuity.
#
# BUG FOUND (fillet.ts:401-405, dialog comment FilletAdvancedOptions.tsx:42):
#   We map isRollingBallCorner → ChFi3d_FilletShape (QuasiAngular vs Rational).
#   ChFi3d_FilletShape is the SURFACE form (rational/quasi-angular/polynomial),
#   NOT the corner solution. So the "Rolling Ball Corner" toggle changes the wrong
#   thing, and conflates with G2 (which also picks a ChFi3d_FilletShape). The
#   toggle gives a false impression that corner behavior is wired — it isn't.
#
# OCC REALITY: BRepFilletAPI_MakeFillet computes vertex corners AUTOMATICALLY and
#   exposes NO rolling-ball-vs-setback toggle and NO per-vertex setback distance.
#   So isRollingBallCorner / setbackDistance cannot map to OCC today — they are
#   round-trip-only (dialog already says this). The corner FAILURE is OCC's
#   vertex-blending weakness, not a missing option. WASM does not help — the
#   kernel is already WASM; this is an API-usage / strategy problem.
